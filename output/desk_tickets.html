1 · How I evaluate the agents on each ticket, and why

This team touches money and customers, so I score in order of what a shop owner can't afford to get wrong. A cheap, fast run that pays the wrong bill is a fail. A correct run that wastes tokens is only a cost problem.

  • Where the plan was right: no ticket sent every specialist to work. Facilities only worked 102, and Customer Service only worked the two customer tickets. Money moved only through human clicks.
  • Where the plan was wrong: it assumed 101 → 102 → 103. The real order was 102 → 101 → 103 because of a board selection bug, so 103 saw Bulldog already unblocked.   • Where the agents did worse than planned: they didn't share what had already been done. In 101, Boss re-asked Accounting about work Inventory had already handed to Accounting. In the earlier 103 run, Inventory asked Accounting to pay 501 again even though 101 had already requested it.

3 · What would have been simpler as one agent with tools, and why

All three tickets. At this size, one agent with the same MCP tools (minus decide_approval) would have been simpler, cheaper and, on 103, probably better:

  • 102 is one straight line. get_ticket → get_lease_rent_due → get_cash_balance → request_payment_approval → update_ticket. The team spent 3 agent loops, 12 model calls and 18.3k tokens on it, and 5 of its 10 tool calls were Facilities and Accounting re-reading get_ticket / get_shop_date that Boss had already read. Every handoff re-sends instructions and context.
  • 101's duplicate work disappears. One agent remembers it already requested approval #2. It wouldn't create the redundant Boss → Accounting branch or the refused duplicate request (4 duplicate tool calls in the final run, 5 in the earlier one).
  • 103 needs one head holding two facts. Inventory knew "short 12, Bulldog can ship". Accounting knew "checking $160, cost $22". No single agent held both, so nobody said "$264 doesn't fit". One agent with all the results in its own context would see it, and could write the draft with the 15% offer it had just priced.
  • Safety doesn't depend on the team. Human approval, no overdraft, the vendor block and drafts-only are all enforced in the MCP server, so one agent would be exactly as safe.

When the team earns its cost: many tickets in parallel, much larger tool sets per domain (real accounting or inventory systems), stricter least-privilege (Customer Service truly can't touch money), and per-role audit. For three tickets and 20 tools, the team's value here was mostly the readable audit and dashboard, not better decisions.

5 · Three new problems this team could not solve, and what we'd need to build

New problemWhy today's app can'tTools and agents we'd add
The Yale AI Club says yes to 8 hoodies now at 15% and 12 later (the natural next step of 103). No tool records a sale, reserves or reduces inventory, bills the club, or takes money in. The rules say cash only goes out, and no tool adds stock when a purchase order arrives. Sales / Orders agent with create_customer_order, reserve_stock / fulfil_order (reduce inventory), create_customer_invoice, record_payment_received, and an Inventory tool receive_shipment (add stock when a PO lands). New tables: orders, receivables. Human approval for discounts above a threshold.
Cash crunch: checking is $160 after this run, October rent ($2,400) is due 2026-10-02, and the 12-hoodie restock costs $264. Agents can only see today's balance. There's no forecast, no scheduled or partial payments, no vendor terms, and no income. The 103 run shows the cost: nobody connected $264 with $160. Treasury agent with cash_forecast(days) (built from leases.next_due, open invoices, pending POs and expected receivables), schedule_payment(date), request_partial_payment, and a human-only request_credit_line. Accounting would call it before every request ("does this still fit next month?").
Tickets arrive by email and time moves on: a new order comes in, Bulldog's tee should arrive 2026-09-05, and Tauhid should actually get a message. No create_ticket tool (the three tickets were pre-loaded). desk.date_today never advances, so a paid PO never "arrives". Drafts can never be sent; that's correct for the homework, but a real shop needs it. Intake agent with create_ticket from a parsed inbox. A scheduler with advance_shop_date and follow-up reminders that re-run Boss on due dates. A Comms tool send_message(draft_id) gated by human approval, with an outbox table and an audit line per send.

What I'd change first

  1. Give Boss a shared ticket memory (approval ids, facts already gathered) and pass it into every delegation. That removes 101's duplicates and the repeated get_ticket / get_shop_date calls.
  2. Make Accounting call get_cash_balance for any restock it hears about, and say "doesn't fit" out loud (103's $264 vs $160).
  3. Require customer drafts to carry Boss's final decision (the 15% offer, "8 now"), and let only Boss mark a customer ticket resolved.
  4. Try a single-agent version on the same three tickets from a reset and compare tokens, cash end state and drafts. The audit trail makes that an A/B test.
